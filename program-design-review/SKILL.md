# Program Design Review

以可复现的运行行为为主证据，对真实程序进行产品设计走查。默认只诊断；只有用户明确要求修改、修复或发布时才改变代码、数据或线上状态。

## 先建立审查基准

1. 确认审查对象：本地程序、测试环境或线上版本，以及对应路径、URL、分支和版本。
2. 确认需求基准：用户请求优先；PRD、Figma 和历史说明用于判断预期，不证明程序已经实现。
3. 选择 1–3 条最关键用户任务进行端到端验证，避免孤立检查页面。
4. 缺少账号、权限、测试数据或后端配置时，继续完成可验证部分，并明确标记未验证范围。

## 证据规则

每项结论使用一种证据等级：

- **已复现**：在当前版本中实际触发，并观察到结果。
- **代码证据**：由代码、接口、数据库结构或测试直接支持，但尚未在界面中触发。
- **推断**：由现有信息合理推断，必须说明推断依据。
- **待验证**：当前条件不足，不能下确定结论。

不得用页面存在、按钮有文案或测试数据固定返回，证明后端功能真实可用。不得把一次成功请求扩展为所有环境都可靠。

## 走查流程

1. 阅读必要的入口、路由、状态模型、接口和持久化代码，建立最小系统地图。
2. 在可运行环境中依次执行关键任务，检查入口、操作、反馈、返回、保存、刷新恢复和终止状态。
3. 对关键写操作核对请求、响应、权限、数据库结果和重新加载后的状态。
4. 检查与任务相关的加载、空、失败、禁用、权限拒绝、长内容、重复提交和恢复路径。
5. 在目标移动端与桌面尺寸下检查滚动、固定导航、安全区、溢出、遮挡和触控区域。
6. 对照 PRD 或 Figma 时，区分“实现错误”“设计稿未同步”和“需求本身未定义”。
7. 归并同一根因造成的多个表现，按对核心任务的影响排序。

执行详细检查时读取 [references/checklist.md](references/checklist.md)。不要机械输出清单中与当前产品无关的项目。

## 严重程度

- **P0**：核心服务不可用、数据破坏、越权或严重隐私风险。
- **P1**：核心任务无法完成、状态错误、用户可能误操作且难以恢复。
- **P2**：明显影响理解、效率、可信度、响应式布局或一致性。
- **P3**：不阻碍任务的视觉和表达优化。

不确定性不会自动提高严重程度。未复现的问题不得写成 P0。

## 输出要求

先给出审查版本、覆盖的用户任务、总体结论和未验证范围。每个问题必须包含：

1. 严重程度和证据等级；
2. 页面、路由、操作步骤或代码位置；
3. 当前表现与预期表现；
4. 对用户任务或数据的具体影响；
5. 最小修复建议；
6. 可执行的验收方法。

只输出能定位、能解释、能验证的问题。没有发现问题时，说明实际覆盖范围，不声称整个产品绝对没有问题。

## 修改与复查

用户授权修改时：

- 保留无关的用户改动，不扩大修改范围；
- 先修根因，再处理视觉表象；
- 对高风险写操作使用隔离测试数据；
- 完成编译、相关自动化测试和关键路径复测；
- 分别报告已修复、仍待验证和因权限无法完成的事项；
- 未经明确授权不发布、不修改生产数据、不改变账号或共享权限。
