# Figma Design Review

以 Figma 文件中的真实节点、属性和原型连接为证据进行设计走查。默认只读审查；只有用户明确要求修改或同步时才写入文件。

## 先建立审查基准

1. 确认 file key、页面和目标节点，记录审查时的文件版本或日期。
2. 先读取文件结构和节点元数据，再选择需要视觉查看的关键页面；不要只凭一张截图判断整个文件。
3. 用户请求是最高范围基准。PRD 说明预期，线上程序说明当前实现，二者都不会自动覆盖 Figma。
4. 选择 1–3 条核心用户流程，列出对应 frame 和连接，再检查视觉细节。

## 证据规则

- **节点证据**：由节点类型、尺寸、约束、自动布局、组件实例、变量或 prototype 属性支持。
- **视觉证据**：由 Figma 原生渲染或节点导出直接观察到。
- **推断**：由画面或命名推断的意图，必须显式标记。
- **待验证**：权限、额度、缺失节点或未提供需求导致无法确认。

没有 prototype connection 只能证明当前文件没有连接，不能直接证明最终程序按钮失效。静态页面存在也不能证明完整交互已经实现。

## 走查流程

1. 枚举相关页面、顶层 frame、组件集、变量和原型起点，识别重复稿、旧稿和当前稿。
2. 按核心流程检查入口、主操作、返回、取消、确认、错误、恢复和终态是否有对应设计。
3. 检查组件复用、variant、状态命名、变量绑定和局部覆盖，定位系统性不一致。
4. 检查自动布局、约束、文本尺寸、裁切、长内容和目标设备适配，不用视觉近似代替属性证据。
5. 检查文案、信息层级、触控区域、对比度、焦点与禁用表达。
6. 与 PRD 或程序对照时，分别标记设计缺失、实现偏差和需求未定义。
7. 合并同一组件或 token 根因引起的跨页问题，优先修复系统层而非逐页打补丁。

执行详细检查时读取 [references/checklist.md](references/checklist.md)。

## 严重程度

- **P0**：关键交付文件损坏、核心流程不可表达或可能导致高风险误操作。
- **P1**：核心流程断裂、关键状态缺失、设计含义明显错误。
- **P2**：组件、布局、文案或适配问题明显影响理解和交付。
- **P3**：不阻碍任务的视觉精修和文件整理。

## 输出要求

先报告文件、页面、节点范围、核心流程和未验证范围。每项问题包含：

1. 严重程度和证据类型；
2. 页面名、frame 名和 node ID；
3. 当前属性或视觉表现；
4. 对用户理解、流程或开发交付的影响；
5. 建议修改的组件、变量、节点或原型连接；
6. 修改后的 Figma 验收条件。

不要使用“看起来不高级”等不可验证措辞。不要把本地 SVG、浏览器截图或生成稿描述成已经写入线上 Figma。

## 修改与复查

获得修改授权后：

- 优先修改组件、variant 和变量，再同步实例；
- 保留用户原有页面和无关内容，避免整页替换；
- 删除节点、覆盖主组件或改变共享库前必须确认影响范围；
- 使用原始矢量或直接节点导出，不用模糊截图替代原图；
- 写入后重新读取目标节点，检查尺寸、布局、连接和命名；
- 工具额度或权限阻塞时停止重复调用，报告真实状态并提供可编辑源文件。
