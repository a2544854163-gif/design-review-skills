# Portfolio Design Review

以“面试官能否快速理解项目、相信关键结论并看清设计能力”为目标走查作品集。默认只输出诊断；只有用户明确要求修改或导出时才编辑源文件。

## 先建立审查基准

1. 确认源文件、导出文件、目标岗位、使用场景和当前版本。
2. 优先检查可编辑源文件，并逐页渲染后判断真实版面；不能只读文本对象或缩略图。
3. 梳理项目可证明事实：真实研究、设计决策、Figma 原稿、已实现功能、测试结果、规划能力。
4. 选择项目自身最合适的叙事顺序，不机械复制另一项目的章节和措辞。

## 证据规则

所有关键主张归入：

- **已实现**：有程序、数据结构、接口、设计文件或可复现行为支持。
- **已验证**：有真实访谈、测试记录、指标或样本支持，并说明样本边界。
- **设计决策**：由需求、约束和权衡支持，但不是研究结论。
- **假设／规划**：尚未验证或实现，必须明确标注。
- **无法核实**：缺少原始材料，不得写成确定事实。

竞品缺点、用户画像、市场结论、商业数字和测试效果必须有来源；没有证据时改写为定位判断或待验证假设，不能补造结果。

## 走查流程

1. 用一句话复述项目解决的问题、目标用户、核心机制和最终成果，检查是否能从封面与前几页得到。
2. 建立“问题与证据 → 洞察 → 设计目标 → 产品机制 → 关键流程 → 异常与兜底 → 实现与验证 → 结果与反思”的因果链；顺序可按项目调整。
3. 删除不推进因果链的重复页面、元话语和只说方法不说结论的内容。
4. 核对每项能力属于设计、原型、后端实现、线上功能还是未来规划。
5. 检查用户画像和研究是否体现真实行为、目标、阻碍和设计影响，而非人口标签或研究计划。
6. 检查商业逻辑是否解释价值对象、使用场景、成本与可持续路径，并与当前产品阶段相称。
7. 逐页渲染检查层级、留白、对齐、图片比例、移动端展示、字体、裁切、重叠和清晰度。
8. 检查跨项目风格统一，但不要求所有项目使用相同叙事模板。

执行详细检查时读取 [references/checklist.md](references/checklist.md)。

## 严重程度

- **P0**：重大事实失实、文件损坏、无法打开或关键内容不可读。
- **P1**：项目逻辑断裂、核心贡献不清、关键结论无证据或页面严重错版。
- **P2**：重复、措辞、信息层级、图片质量或章节顺序明显削弱表达。
- **P3**：不影响理解的视觉精修。

## 输出要求

先给出目标岗位、审查文件、项目叙事摘要、总体判断和最需要优先修复的三项。每个问题包含：

1. 严重程度与证据状态；
2. 页码和页面标题；
3. 当前表达或版面；
4. 为什么会影响面试官理解或可信度；
5. 建议保留、删除、合并、改写或重排的具体方式；
6. 验收条件。

不要输出只适用于作者内部协作、却不应给面试官看的元话语。不要用“高级感不足”代替具体的层级、对齐、比例或证据问题。

## 修改与复查

用户授权修改时：

- 保留原文件，输出清晰命名的新版本；
- 优先使用 Figma 或源文件直接导出的原图，保持设备比例，不用浏览器截图替代；
- 不虚构访谈、数据、竞品缺陷、技术实现或商业结果；
- 修改内容后重新渲染全稿，检查溢出、重叠、裁切、字体替换和图片清晰度；
- 检查目录、页码、项目编号、跨页术语和结论是否同步；
- 只报告实际完成的编辑和实际执行的验证。
